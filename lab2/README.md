# MusicDB

Учебная реализация упрощённой реляционной СУБД на Java 8+ и Maven.

## Возможности

- INTEGER, DOUBLE, STRING, DATE, BOOLEAN
- Первичные и внешние ключи
- CRUD-операции и проверка типов и ограничений
- Сохранение и восстановление JSON через Gson 2.10.1
- Атомарная замена файла хранилища
- Неуникальные HashMap-индексы и автоматический поиск по равенству
- SQL: CREATE INDEX, SELECT, INSERT, UPDATE, DELETE

## Структура

- `core` — модели и логика базы данных
- `storage` — сохранение и загрузка
- `index` — `HashIndex`, `IndexManager` и определения индексов
- `sql` — `SqlParser`, `SqlCommand`, `QueryExecutor`
- `benchmark` — генератор и отдельный инструмент измерений
- `src/test/java` — JUnit 5 тесты
- `docs` — документация, включая [диаграммы индексации](docs/indexes.md)

## Предметная область

Музыкальная библиотека: artists, albums, songs. Таблицы создаются существующим
`MusicDatabaseSchema.createTables(engine)`. В исходном проекте SQL-слоя и CLI
не было; добавлен небольшой SQL-слой над существующим `DatabaseEngine`.

## Система индексации

`HashIndex` хранит `HashMap<Object, List<Row>>`: одному типизированному ключу
соответствуют все строки с этим значением. Например, ключ `"USA"` возвращает
нескольких исполнителей. Пустые группы удаляются. Повторное добавление одного
объекта строки не создаёт дубль. `null` также может быть ключом.

Значения приводятся через существующий `DataType.convert`: числа, даты и
логические значения остаются соответствующими Java-типами. Строки сравниваются
с учётом регистра, имена таблиц, столбцов и индексов — без учёта регистра.
SQL-литералы условий приводятся к типу столбца в `QueryExecutor`.
Для прямого Java API сохранена прежняя семантика `Condition.matches`: если
тип условия не подходит для HashMap-ключа, используется полный перебор.

`IndexManager` проверяет имена и дубли, строит и регистрирует индексы на таблицах,
восстанавливает их и удаляет определения при удалении таблицы.
`QueryExecutor` вызывает существующий движок; выбор между индексом и полным
перебором выполняется в `Table.select`, поэтому ускоряется и прямой Java API.
Индекс используется только для `EQ`. Остальные сравнения и запросы без WHERE
сохраняют полный перебор. Результат в обоих случаях содержит копии строк.

Поиск группы в HashMap в среднем занимает O(1), чтение и копирование k результатов
— O(k). Для сохранения прежнего порядка строк результаты индекса сортируются
по внутреннему порядку добавления: до O(k log k). Для этого используется
`IdentityHashMap<Row, Long>`. Эти номера служат только для порядка внутри памяти,
не являются идентификаторами строк и не сохраняются на диск.

## SQL и примеры

Поддерживается одна команда за вызов, необязательная завершающая `;`,
регистронезависимые ключевые слова. Идентификаторы: `[a-zA-Z_][a-zA-Z0-9_]*`.
Имя индекса уникально в пределах базы; на один столбец допускается один индекс.

```sql
CREATE INDEX idx_artists_country ON artists (country);
SELECT * FROM artists WHERE country = 'USA';
SELECT name, country FROM artists WHERE country = 'USA';
INSERT INTO artists (id, name, country, is_active)
VALUES (1, 'Artist', 'USA', true), (2, 'O''Brien', 'UK', false);
UPDATE artists SET country = 'Canada' WHERE id = 1;
DELETE FROM artists WHERE country = 'UK';
```

WHERE поддерживает одно сравнение: `=`, `!=`, `<>`, `>`, `<`, `>=`, `<=`.
Литералы: строки в одинарных кавычках (кавычка внутри — `''`), числа, TRUE,
FALSE, NULL; даты передаются строками ISO `YYYY-MM-DD`. Отсутствие WHERE
означает все строки, в том числе для UPDATE и DELETE. Сохранена семантика ядра:
`WHERE column = NULL` выбирает строки с null, это отличается от стандартного SQL.

Пример использования из Java (импорты `core.*`, `sql.*`, `storage.*`):

```java
DatabaseEngine engine = new DefaultDatabaseEngine(new JsonStorageManager("data/music.json"));
// Только для новой базы: MusicDatabaseSchema.createTables(engine);
QueryExecutor executor = new QueryExecutor(engine);
executor.execute("CREATE INDEX idx_artists_country ON artists (country)");
@SuppressWarnings("unchecked")
List<Row> rows = (List<Row>) executor.execute("SELECT * FROM artists WHERE country = 'USA'");
```

`execute` возвращает `List<Row>` для SELECT, число изменённых строк для CRUD,
`null` для CREATE INDEX. Ошибки SQL, неизвестные объекты, неправильные значения
и конфликты индексов сообщаются через `IllegalArgumentException`.
Можно также вызвать `execute(new SqlParser().parse(sql))`.

## Актуализация индексов

- INSERT: после нормализации и проверки строки `Table.insert` добавляет фактически
  сохранённый объект во все индексы таблицы.
- UPDATE: ядро создаёт новые объекты Row. Старые объекты остаются в резервном списке.
  После проверки ограничений `HashIndex.replace(oldRow, newRow)` заменяет ссылки;
  при изменении ключа удаляет старую группу и добавляет новую. Если ключ прежний,
  ссылка заменяется внутри прежнего списка. Порядок результатов сохраняется.
- DELETE: строка удаляется из всех групп; последняя строка удаляет ключ группы.

При ошибке пакетного INSERT, UPDATE, проверки внешнего ключа или сохранения CRUD
движок восстанавливает прежние строки и перестраивает индексы. Ошибка сохранения
CREATE INDEX отменяет его определение. Обычные успешные изменения обновляют
индексы по строкам, без полной перестройки. SQL и прямые вызовы движка проходят
через одну логику Table.

## Сохранение и восстановление

В существующем JSON базы рядом с `tables` сохраняется только список определений:

```json
{"indexes": [{"name": "idx_artists_country", "table": "artists", "column": "country"}]}
```

Менеджер, HashMap, списки ссылок на Row и служебный порядок помечены `transient`
на уровне владеющих полей и не сериализуются. `JsonStorageManager.load` сначала
читает таблицы, восстанавливает значения согласно схеме (в том числе INTEGER
вместо загруженного Gson Double и DATE вместо строки), затем строит индексы.
Они ссылаются на актуальные объекты загруженных строк. Старые файлы без `indexes`
загружаются с пустым списком индексов. Перестройка сначала очищает регистрацию,
поэтому повторный вызов не создаёт дубли. Сохраняется прежний механизм атомарной
замены JSON-файла.

Автосохранение выполняет `DefaultDatabaseEngine`. При непосредственном изменении
Table или использовании `IndexManager.create` владелец Database сам вызывает
`StorageManager.save(database)`.

Нужны JDK 8+ и Maven. Зависимости и версии в `pom.xml` не изменены.

```bash
mvn clean test
```

0 ошибок, 0 падений, 0 пропусков**. Покрыты дубликаты и типы ключей,
создание индексов и ошибки SQL, выбор индексного пути, эквивалентность результатов,
последовательность INSERT → UPDATE → DELETE, откаты ошибок, JSON и повторная

## Генератор и бенчмарк

`TestDataGenerator.generate(size)` создаёт базу в памяти с seed 42, уникальными
INTEGER id и 1000 повторяющимися значениями `country_0` … `country_999`.
Тестовые строки заполняются напрямую до создания индексов, чтобы подготовка
100 000 записей не зависела от квадратичной проверки первичного ключа в INSERT.
Этот путь предназначен только для подготовки заведомо корректных данных.

После компиляции:

```bash
mvn test
java -cp target/classes com.team.dbms.benchmark.QueryBenchmark
# Выбор размера, например:
java -cp target/classes com.team.dbms.benchmark.QueryBenchmark 10000
```

Бенчмарк использует существующий движок с хранилищем в памяти. Сначала измеряется
полный перебор, затем на тех же объектах создаётся индекс и измеряется поиск.
Используются одинаковые 8 условий: семь значений country и одно отсутствующее.
Перед замерами сравниваются все значения и порядок результатов обоих способов.
Для каждого способа выполняются 200 запросов прогрева, затем 9 серий по 40
запросов. Время — медиана времени серии, делённая на 40, через `System.nanoTime()`.
Результаты потребляются через volatile-счётчик. В поиск входят фильтрация и
создание обычных копий результатов; разбор SQL, генерация, построение индекса,
проверка результатов, файловый ввод-вывод и вывод в консоль исключены.
Подготовка и построение индекса показываются отдельно.

## Ограничения

- Только неуникальные индексы одного столбца для равенства; диапазоны сканируются.
- Нет JOIN, AND/OR, ORDER BY, составных индексов, DROP INDEX и SQL CREATE TABLE.
  Схемы и удаление таблиц доступны через существующий Java API. CLI не добавлен.
- Прежняя проверка первичных ключей при INSERT остаётся линейной; индексирование
  ускоряет SELECT и добавляет расходы на память и изменение данных.
- База рассчитана на один поток, без транзакций между несколькими командами.
- `getRows()`, `getValues()` и другие существующие изменяемые коллекции доступны
  как раньше. Прямое редактирование строк/коллекций в обход CRUD не поддерживает
  индексы автоматически; прикладной код должен использовать движок или Table CRUD.
- Минимальный бенчмарк без JMH не изолирует GC/JIT/нагрузку ОС; результаты
  функциональных тестов от измеренной скорости не зависят.
